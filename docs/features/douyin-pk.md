# 抖音 PK 分数

录制抖音直播时，PK（连麦对战）的分数快照会随弹幕 XML 一并保存，并可在浏览器里按场次查看。

::: tip 适用范围
仅抖音支持。B站、斗鱼、虎牙、小红书、TikTok 不采集 PK 数据。
:::

## 开启与关闭

| 层级       | 位置                                                                  |
| ---------- | --------------------------------------------------------------------- |
| 全局配置   | 设置 → 录制 → **保存PK分数**                                          |
| 单房间配置 | 录制工具 → 添加/编辑直播间 → **保存PK分数**（右侧可勾选「全局」跟随） |

- **默认开启**。
- 这两项只在「弹幕录制」开启时显示 —— 关闭「弹幕录制」后 XML 本身就不会生成。
- 关闭后：XML 里不写 `<pk>` 与 `<pk_users>`，网页预览也不显示任何 PK 区块与导航项。

## 数据写在哪儿

与弹幕同目录、同一个文件：`<视频文件名>.xml`。

### `<pk>`：一次分数快照

```xml
<pk timestamp="1792161263973" ts="276.448" battle_id="7697274000687518746">
  <player uid="58295419229" score="22" rank="1"/>
  <player uid="65305021017" score="2" rank="2"/>
  <player uid="1839899955955708" score="0" rank="3"/>
</pk>
```

| 属性                                      | 含义                                                                          |
| ----------------------------------------- | ----------------------------------------------------------------------------- |
| `timestamp`                               | 绝对时间戳（毫秒）。可在设置里切换为服务端时间戳                              |
| `ts`                                      | 距本次录制开始的秒数（保留毫秒），便于阅读与排序                              |
| `battle_id`                               | 单场 PK 的标识。一场直播可打多场 PK，靠它把快照归到对应场次；缺失时不写该属性 |
| `player/@uid`                             | 选手房间号 uid                                                                |
| `player/@score`                           | 当前分数                                                                      |
| `player/@rank`                            | 当前名次                                                                      |
| `player/@team_score`、`player/@team_rank` | **仅团队 PK** 时出现；非团队 PK 不写这两个属性                                |

PK 进行期间抖音会持续推送分数，**大约每秒产生一条 `<pk>`**（实测一场约 4 分钟、233 条、3 名选手 = 699 个 `<player>`），所以数据量主要取决于 PK 时长。

### `<pk_users>`：昵称映射表

```xml
<pk_users>
  <user uid="1839899955955708" nick="李真棒🥇🌊🍭（美妆蛋）"></user>
  <user uid="58295419229" nick="小好"></user>
</pk_users>
```

**为什么单独一张表**：抖音的 PK 分数消息**只带 uid 与分数、不带昵称**，而 XML 是单向追加、无法回改。因此昵称统一在**录制结束时**追加到文件末尾，预览时按 `@uid` 查表翻译。

- 只有真正拿到昵称的选手才会写入；查不到的选手预览时直接显示 uid。
- 昵称来源优先级：PK 开始/结束消息里的 `userInfos` 优先，接口反查只用于补缺。

## 网页预览

用 Chrome / Edge / Firefox 直接打开 XML 即可（文件内嵌 XSL 样式）：

- PK 快照按 `battle_id` 分组，每场 PK 一个可折叠区块，标题带场次序号与 `battle_id`。
- 表格列为：PK 时间 / 主播 / 主播ID / 分数 / 排名。
- **团队 PK 场次**会额外显示「团队分数」「团队排名」两列；非团队场次不显示这两列，也不会留下空列。
- 「主播」列显示 `<pk_users>` 里的昵称，查不到则显示 uid。
- 关闭「保存PK分数」后，预览页面里不会出现 PK 相关区块与导航项。

## 已知限制

1. **昵称依赖 PK 事件**：只有收到 PK 开始/结束消息里的 `userInfos` 才能直接拿到昵称。中途接入（录制开始时 PK 已在进行）只能靠接口反查，接口也查不到时显示 uid。
2. **`battle_id` 缺失时不分组**：极少数情况下抖音不下发场次标识，此时所有快照会集中到同一个区块。
3. **录制期不发起昵称查询**：为避免额外请求与风控风险，昵称反查统一推迟到录制结束前批量执行。

## 调试：原始报文落盘

排查「某个 uid 全程显示为 uid」这类问题时，可以开启 PK 原始消息转储。

开启后，每条 PK 原始消息按行写入 JSONL，与视频同目录：

```
<视频文件名>_pk_raw.jsonl
```

每行形如 `{"tag":"linkMic","at":<毫秒时间戳>,"payload":{…}}`，其中 `tag` 为 `linkMic` / `linkMicBattle` / `linkMicBattleFinish`，便于用 `grep` / `jq` 过滤。

**默认关闭** —— 这是排查用的临时产物（单场几百 KB），关闭时不会创建任何文件。

开启方式二选一（**取或**，任一为真即开启）：

1. 设置 → 录制 → 抖音 → 调试 → **PK 原始报文**（打包版唯一可行的方式，改完对下一场录制生效）；
2. 启动前设环境变量：

| shell      | 命令                                   |
| ---------- | -------------------------------------- |
| PowerShell | `$env:BILILIVE_TOOLS_PK_RAW_LOG = "1"` |
| cmd        | `set BILILIVE_TOOLS_PK_RAW_LOG=1`      |
| bash       | `export BILILIVE_TOOLS_PK_RAW_LOG=1`   |

环境变量在每次创建写入器时读取，因此同一进程内改动对后续录制会话生效。

::: tip 打包版请用设置页开关
从图形界面启动的应用**不继承**终端里设置的环境变量，此时设环境变量不会生效。详见[排障与调试](/features/debug)。
:::

::: warning 分段录制时的文件名
分段录制时，视频文件名在**录制中**是底层工具的命名模板（ffmpeg `-PART%03d`、mesio `-PART%i`），
`%03d`/`%i` 会被替换成段号，且每段结束时程序还会把它重命名为「命名规则」生成的名字 ——
**录制结束后磁盘上的视频既没有 `PART`，也没有占位符**。

只有转储文件例外：它的基名取自那个**未替换的模板字符串**，并且从不重命名，所以会看到：

```
<视频文件名>-PART%03d.flv_pk_raw.jsonl
```

该转储仍**只按录制会话生成一个**，不随分段切割，覆盖整个会话的所有分段。但这个名字**不对应任何一个真实视频**，
清理时请按 `*_pk_raw.jsonl` 通配查找。各引擎的完整规则（mesio 的 `%i`、录播姬无占位符、按大小分段的情况）
见[排障与调试](/features/debug)。
:::

体量与清理说明见[排障与调试](/features/debug)。
