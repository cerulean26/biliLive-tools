# 抖音礼物图标与头像

录制抖音直播时，礼物消息里的**礼物图标**与**送礼者头像**会随弹幕 XML 一并保存，可在浏览器预览里直接看到图片。

::: tip 适用范围
仅抖音支持。图标/头像只在有数据时才写入，其他平台不会留下空属性。
:::

## 开关

两项可分别关闭：**设置 → 录制配置 → 抖音 → 弹幕**；「添加直播间」弹窗里也有同样两项，可勾「全局」跟随设置。

| 开关                             | 关闭后                                      |
| -------------------------------- | ------------------------------------------- |
| 礼物图片（`saveGiftIcon`）       | XML 不写 `<gi>` 表，预览「图标」列整列消失  |
| 送礼用户头像（`saveGiftAvatar`） | 礼物行不带 `a` 属性，预览「头像」列整列消失 |

两者默认开启，但**依赖「弹幕录制」与「保存礼物」**——任一项没开时这两个开关置灰：礼物消息本身都没保存，图片自然是无源之水。关闭后该列**连表头一起不渲染**，不会留下整列空格（判据是文档里有没有 `/i/gi` 与 `/i/gift[@a]`，两处 `<th>`/`<td>` 用同一条件，列数因此始终对齐）。

实测（238 条礼物的产物）：两项都关闭时 XML 46,193 B，开启时 52,599 B，省 **12.2%**。

## 数据写在哪儿

与弹幕同目录、同一个文件：`<视频文件名>.xml`。

图片地址只存**相对路径**（如 `webcast/5ddf….png`），不存完整 URL —— CDN 域名与模板参数会轮换，存相对路径才不会随域名变更而失效。拼接规则见[「如何拼出完整 URL」](#如何拼出完整-url)。

### `<gi>`：礼物图标表

```xml
<!-- 同名不同 ID：三张图各不相同，必须分开 -->
<gi i="6937" n="点亮粉丝团" u="webcast/5ddfcd51….png"/>
<gi i="6938" n="点亮粉丝团" u="webcast/d4006cb1….png"/>
<!-- 同 ID 不同名：也要分开，否则三个名字都显示首见的同一张图 -->
<gi i="685" n="粉丝团灯牌" u="webcast/3d2367ee….png"/>
<gi i="685" n="点点星光" u="webcast/….png"/>
```

| 属性 | 含义                                                      |
| ---- | --------------------------------------------------------- |
| `i`  | 礼物 ID。**表内不唯一** —— 同一 ID 可以有多行（不同名字） |
| `n`  | 礼物名。**是键的组成部分**，不能省略                      |
| `u`  | 图标相对路径                                              |

**查表的键是 `(i, n)`，不是 `i` 单独一个。** 实测两个方向都不是 1:1：

| 方向         | 实测                                                           |
| ------------ | -------------------------------------------------------------- |
| 同名不同 ID  | 「点亮粉丝团」→ `6937` / `6938` / `6939`，三张图标各不相同     |
| 同 ID 不同名 | `685` → 粉丝团灯牌 / 点点星光 / 闪烁星河（价格相同、时间交错） |

只用 ID 时，第二种情况会取首见图、三条显示同一张；只用名字时，第一种情况会取首见图。所以两个都要进键。

拼接无歧义：`giftId` 是纯数字，不含分隔符 `|`，因此任意两组不同的 `(id, 名字)` 拼出的键必不相同。`giftId` 为空时键退化成 `|礼物名`，首段仍不含 `|`，与任何数字 id 的键都不相等 —— 所以空 id 照样建表，不能跳过；代价是这一行失去了同名区分能力（见已知限制第 8 条）。

XSL 侧用 `concat(@i,'|',@n)` 建索引，与 `<gift>` 上的 `concat(@giftid,'|',@giftname)` 一一对应：

```xml
<z:key name="giById" match="gi" use="concat(@i,'|',@n)"/>
```

::: warning key 的定义与查询必须同步改
任一侧退回单键，`key()` 就返回空集，**图标会全部消失且不报错**。改动时必须两处一起改，并跑
`packages/liveManager/test/xml_stream_controller_gift_icons.test.ts` 里那个「key 定义与查询都用复合键」的用例。
:::

因此 `<gift>` 上的 `giftid` 与 `giftname` **两个都要进键，缺一不可**：同名不同 ID 只能靠 `giftid` 区分，去掉它就退回「只按名字」的错。

唯一的特例是「消息里根本没下发 `giftId`」：这时不写 `giftid` 属性（省字节），XPath 里不存在的属性按空串参与 `concat`，键变成 `|礼物名`，与声明行的 `<gi i="">` 对得上。这是**降级不是等价**——那份产物在这个礼物名上就失去了同名区分能力（见已知限制第 8 条），并没有变成「只用名字建键」。

```xml
<gift ts="0.5" giftname="点亮粉丝团" giftid="6937" giftcount="1" price="1000" user="甲" uid="334723570733996"/>
<!-- giftId 为空：无 giftid 属性，靠 <gi i="" n="…"> 对上 -->
<gift ts="9.2" giftname="小心心" giftcount="1" price="100" user="甲" uid="334723570733996"/>
```

### `<gift>` 上的 `a`：送礼者头像

头像**内联在首条礼物上**，没有单独的映射表：

```xml
<!-- 该 (uid, 昵称) 第一次送礼（带头像）：多一个 a -->
<gift ts="0.5" giftname="点亮粉丝团" giftid="6937" giftcount="1" price="1000" user="甲" uid="334723570733996" a="100x100/aweme-avatar/tos-cn-abc"/>

<!-- 同一用户之后送礼：不再重复写 a，靠 (uid, 昵称) 反查 -->
<gift ts="9.2" giftname="小心心" giftid="463" giftcount="1" price="100" user="甲" uid="334723570733996"/>
```

键是 **`(uid, 昵称)`**，不是 `uid` 单独一个。XSL 用「带头像的礼物」建索引，每条礼物按自己的 `(uid, user)` 反查首见：

```xml
<z:key name="giftAvatarByUser" match="gift[@a]" use="concat(@uid,'|',@user)"/>
<!-- 渲染任意一条礼物时 -->
<z:variable name="av" select="key('giftAvatarByUser',concat(@uid,'|',@user))[1]/@a"/>
```

`[1]` 取文档序首见，结果与批次顺序无关；第二次送礼那条虽然没有 `a`，但 `uid` 与 `user` 一直在，仍能查到同一张头像。

::: danger 为什么不能用 `uid` 作键（实测反例）
抖音有**匿名占位 uid `111111`**，多个互不相干的匿名身份共用它。实测一份 6 分钟产物里，`dou7702128` / `神秘人397543` / `dou1669765` 三个昵称都用 `uid="111111"`：

- 按 `uid` 去重时只有首个昵称能写 `a`，后两个的头像被**静默丢弃**（不报错）；
- 渲染时它们反查到首条那个人的头像 ⇒ 不同的人显示同一张图（张冠李戴）。

注意「神秘人」不等于匿名共用 uid：`神秘人•S ⁵²⁹⁹`（uid 7630365130980066353）等多数匿名身份其实有独立 uid，按 `uid` 反而没问题。反例只为说明**uid 不保证唯一**，故键必须并入昵称；普通用户 uid 唯一时两种键等价，文件体积不变。
:::

::: warning 键的定义与查询、写入侧去重键必须三处同步
写入侧 `avatarKey(uid, name)`、XSL 的 `<z:key use=…>`、`key(...)` 的查询参数任何一处退回单键，头像都会**静默全部消失或串号**，不报错。对应护栏见 `xml_stream_controller_gift_icons.test.ts` 里「匿名占位 uid 下的不同昵称各写一次头像」用例。
:::

::: warning 为什么不是独立的 `<ui>` 表
早期版本用 `<ui i="" p=""></ui>` 表，实测是**负收益**：表项要把 19 位 uid 与标签骨架再写一遍（约 39 B/行），而 uid 在这条礼物上本来就必须有。真实产物（2175 条礼物 / 1791 个用户）改为内联后省 **49.5 KB（-3.6%）**。若某天要重建这张表，先量「礼物条数 / 头像用户数」——低于 **1.235** 建表就是亏的。
:::

### 为什么是「首见声明」而不是逐条写

一条礼物消息的图片地址约 145 字符，而一场直播往往只有几十种礼物、几百位用户。逐条写会把文件撑大数倍：

| 样本 | 礼物条数 | 逐条写            | 建表后               |
| ---- | -------- | ----------------- | -------------------- |
| A 场 | 1017 条  | +141.5 KB（+97%） | **+46.7 KB（+32%）** |
| B 场 | 71 条    | +9.7 KB（+61%）   | **+3.6 KB（+22%）**  |

声明写在**该礼物/用户第一次出现的那批消息里**（就地），而不是像 `<pk_users>` 那样集中到文件末尾：体积相同，但录制异常中断时已写入的部分不会丢，流式解析也不需要读完整文件。

按「分段」录制时，每个分段各声明一次 —— 仍是按种类数而非条数计算。

但**头像的账相反**：礼物条数 / 头像用户数 = 1.214，低于建表的平衡点 1.235，建表反而更大。所以图标用表、头像内联，两者策略不同不是笔误。

## 网页预览

用 Chrome / Edge / Firefox 直接打开 XML 即可（文件内嵌 XSL 样式）。礼物表列为：

头像 / 用户名 / 用户ID / 图标 / 礼物名 / 礼物数量 / 出现时间

查不到图片时该单元格为空，**不会拼出无效地址**。地址拼对了但图片本身取不到（CDN 换图、403/404、断网）时，`<img>` 上的 `onerror` 会移除自己 —— 单元格留空但不留破图，`<td>` 仍在，列宽与对齐不受影响。

图片一律带 `loading="lazy" decoding="async" onerror="this.remove()"`（三者由源码里的 `GIFT_IMG_ATTRS` 常量统一给出，5 个图片分支共用，所以不会漏某个分支）。一份 19 分钟的产物（2175 条礼物）会产生 4350 个 `<img>`、1802 个唯一 URL（头像 1759 + 图标 43），而表格只在 `max-height:80vh` 的容器里滚动显示，可见不足 20 行。headless Chrome 实测同一结构下 2000 个唯一图片 URL：不加 lazy 全部请求，加 lazy 只请求 **67** 个（-96.7%），并且滚动到哪补到哪（67 → 180）。

## 如何拼出完整 URL

抖音的图片有三类前缀，规则不同：

| 相对路径前缀                | 头像（`<gift a>`）                                           | 图标（`<gi u>`）                                         |
| --------------------------- | ------------------------------------------------------------ | -------------------------------------------------------- |
| `webcast/`                  | `https://p11.douyinpic.com/aweme/100x100/<u>`（自带 `.png`） | `https://p3-webcast.douyinpic.com/img/<u>~tplv-obj.webp` |
| `aweme-avatar/`（缺尺寸段） | `https://p11.douyinpic.com/aweme/100x100/<u>.jpeg`           | 不出现                                                   |
| 其他（含 `100x100/…`）      | `https://p11.douyinpic.com/aweme/<u>.jpeg`                   | `https://p11.douyinpic.com/aweme/<u>.jpeg`               |

礼物图标实测全部是 `webcast/` 开头。头像多数是 `100x100/aweme-avatar/…`（走 `p11`），偶尔是 `webcast/`；**匿名头像还会缺尺寸段**，直接下发 `aweme-avatar/mosaic-legacy_…` —— 这时按「其他」拼成 `…/aweme/aweme-avatar/…jpeg` 会返回 **400 `{"code":2004}`**（破图），必须补上 `100x100/` 段才 200。三类前缀都要判断。

### 为什么头像和图标要走不同 CDN —— 透明通道

礼物图标的源图 **20/20 是 RGBA**（逐像素统计，透明像素占 37%–80%）。p11 的 `100x100` 会把其中 **15 个转成 JPEG**，而 **JPEG 没有 alpha**，透明区被填成**纯黑方块** —— 在浅色表格里非常显眼。所以图标改走 p3 的 `~tplv-obj.webp`：实测 **20/20 保留 alpha**（全部返回带 ALPH 块的 VP8X）。

头像不受这个约束：源图是调色板且无 `tRNS`（本来就不透明），用 p11 只要 3,483 B，换成 webp 反而要 12,666 B。

| 20 个礼物图标合计      | 字节          | 透明                     |
| ---------------------- | ------------- | ------------------------ |
| 原图 `~tplv-obj.image` | 1,008,999 B   | 20/20（但 168–280 px）   |
| p11 `aweme/100x100/`   | **116,254 B** | **仅 5/20**（15 个黑底） |
| p3 `~tplv-obj.webp`    | 174,252 B     | **20/20** ✅             |

采用组合（头像 p11 + 图标 webp）后，真实产物 322 个 img / 127 个唯一 URL：**原图 1,347,289 B → 512,542 B（-62%）**，全部 200。比「头像图标都用 p11」的 454,544 B 多 12.8%，换来图标不出现黑底。

⚠️ `~tplv-obj.<ext>` 只决定**输出格式**，**不缩放**：`.png` 返回的字节与 `.image` 完全一致（md5 相同），`.webp` / `.jpeg` 也只是换编码、像素仍是原尺寸。真正能缩图的只有路径里的尺寸段（`100x100` / `200x200`；`48x48` 不存在，会 400）。

注意 `webcast/` 的 uri 自带扩展名（`.png`），**不要再补 `.jpeg`**；而 `aweme-avatar/` 的 uri 没有扩展名，必须补 `.jpeg`。

XSL 里的写法（已实测）：

**头像**（`$av`，三分支）：

```xml
<z:variable name="av" select="key('giftAvatarByUser',concat(@uid,'|',@user))[1]/@a"/>
<z:if test="string($av)">
  <z:choose>
    <z:when test="starts-with($av,'webcast/')">
      <img height="24" loading="lazy" decoding="async" onerror="this.remove()" src="https://p11.douyinpic.com/aweme/100x100/{$av}"/>
    </z:when>
    <!-- 必须在 otherwise 之前：缺尺寸段时按 otherwise 拼是 400 -->
    <z:when test="starts-with($av,'aweme-avatar/')">
      <img height="24" loading="lazy" decoding="async" onerror="this.remove()" src="https://p11.douyinpic.com/aweme/100x100/{$av}.jpeg"/>
    </z:when>
    <z:otherwise>
      <img height="24" loading="lazy" decoding="async" onerror="this.remove()" src="https://p11.douyinpic.com/aweme/{$av}.jpeg"/>
    </z:otherwise>
  </z:choose>
</z:if>
```

**图标**（`$gu`，两分支 —— 走 webp 而不是 p11，为了保住透明）：

```xml
<z:variable name="gu" select="key('giById',concat(@giftid,'|',@giftname))/@u"/>
<z:if test="string($gu)">
  <z:choose>
    <z:when test="starts-with($gu,'webcast/')">
      <img height="24" loading="lazy" decoding="async" onerror="this.remove()" src="https://p3-webcast.douyinpic.com/img/{$gu}~tplv-obj.webp"/>
    </z:when>
    <z:otherwise>
      <img height="24" loading="lazy" decoding="async" onerror="this.remove()" src="https://p11.douyinpic.com/aweme/{$gu}.jpeg"/>
    </z:otherwise>
  </z:choose>
</z:if>
```

::: warning `test="string($u)"` 不能写成 `test="$u"`
表里可能存着空属性（`u=""`）。`<z:if test="$u">` 对**空的节点集**为 false，但对**值为空的字符串**为 true，会走进 `otherwise` 分支拼出 `…/aweme/.jpeg` 这样的无效地址。用 `string($u)` 取字符串值后再判断才正确。
:::

## 已知限制

1. **同名同 ID 换图**：同一个 `(giftId, 礼物名)` 中途换了图标时，仍取首见的那张 —— 键相同就只能存一张图。实测未出现，但这是「首见即定」策略的固有限制，双键解决不了。
2. **表项的 `i` 不唯一**：同一 `giftId` 可能有多行 `<gi>`（不同礼物名各一行）。自行解析 XML 的消费方若要按 `i` 建索引，必须用 `(i, n)` 作键，否则后者会覆盖前者。
3. **图标可能跨场变化**：同一 `giftId` 的图标 uri 在两次录制之间可能不同（实测「私人飞机」换过图）。表随文件自带，单文件内不受影响；但外部程序若按 `giftId` 做**跨文件**的全局图标缓存，会显示旧图。
4. **匿名身份**：抖音匿名占位 uid `111111` 会被多个不同昵称共用（实测一份 6 分钟产物里 3 个），且各自下发的头像 uri 形态不统一（`aweme-avatar/…` 缺尺寸段 / `webcast/…` / `100x100/aweme-avatar/…`）。键已用 `(uid, 昵称)` 区分、三类前缀都已兜底，但仍是「首见即定」——同一昵称中途换头像不会跟着更新。
5. **头像只有送礼者才有**：头像数据只在礼物消息里下发，没送过礼物的用户不会有 `a` 属性。
6. **同一 `giftId` 的多个名字，只有首见那个有图**：实测 `685` 同时下发 粉丝团灯牌 / 点点星光 / 闪烁星河，但所有产物与原始转储里只记录到 粉丝团灯牌 的 `image.uri`（它总是最先出现）。所以这三个名字的 `<gi>` 会指向同一张图，**三者图标是否真的相同尚未证实**。取证方式：设 `BILILIVE_TOOLS_GIFT_RAW_LOG=1` 录一场，抓到 点点星光 的 `gift.image.uri` 再比对；在此之前不要凭猜测补表项。
7. **`onerror` 只覆盖「取不到」**：HTTP 200 但内容本身是错误占位图（CDN 默认图）不会触发 `onerror`，仍会显示出来。另外样式表是内嵌在 XML 里的，**只有新录制的文件带 `onerror`**，旧产物打开还是老行为（要修只能重新生成样式表）。
8. **`giftId` 缺失时无法区分同名礼物**：键退化成 `|礼物名`，同名不同 id 的礼物会共用首见图。实测 4 份产物（34/161/187/238 条礼物）**0 命中** —— 抖音正常都带该字段，此路只在字段缺失时兜底；修前它会让这类礼物连 `<gi>` 都不写，若全场都缺 id，图标列会整列消失。
